# v1 实验计划（精简版）

> 替代 [experiment-design-v1.md](experiment-design-v1.md) 第 6 节的排期。原计划约 36 GPU 小时（不含 E7）、约 80 次 GPU 运行；精简后约 **5 GPU 小时、41 次 GPU 运行**（其中 38 次是 1.5–6 分钟的短跑）。思路三条：
>
> 1. **已经证明过的不再跑**，只用新代码做一次回归。
> 2. **不需要 GPU 的量放到 CPU 上测**：样本正确性（E4）、每样本请求数、缓存命中率、worker 内存都和模型无关。
> 3. **E3 用"模型 + 验证"代替穷举**：每次抢占的代价 = 恢复耗时 + 重做步数 × 单步时间，这几个量在批次 0–2 里都会测到；用同一份泊松时间表算出成本曲线，再用 3 次真实长跑验证误差。

## 0. 已经证明、不再重跑的

| 结论 | 证据（A100，LIBERO-10） |
|---|---|
| 数据逐比特正确（像素、state/action、顺序） | v0 parity；v1 60/60、80/80 批次指纹 |
| 小数据稳态不吃亏，GPU 是瓶颈 | 等数据占比 0.07%，0.649–0.655 s/步 |
| Lance 比原生省内存 | 16.8–17.0 GB vs 18.9–19.3 GB |
| 原生续训会打乱数据 | `native_pre` 恢复后 0/50 |
| 清洗快、几乎不写盘 | E6：0.296 s vs 1.716 s，0.9 MB vs 604 MB |

所以 **E2 的 S 档、C(v0) 组、D 组、C′ 组、E6 的 S 档都删掉**。

## 1. 删掉或推迟的

| 项 | 处理 | 理由 |
|---|---|---|
| E5 网络扰动 | 推迟 | toxiproxy 准备成本高，不影响三个主问题 |
| E7 训练效果（10 GPU 小时） | 推迟 | 数据逐比特一致已证明，训练效果不会有差别；仿真还要 EGL |
| L 档 350 GB | 等 E1 曲线 | A 组如果随体积线性增长，直接按下载吞吐外推 |
| E8 逐项消融 | 不单开批次 | 每项消融嵌入下面某个批次（见各批次"顺带"一栏） |
| 种子 2 → 1、重复 5 → 3、E2 步数 2000 → 500 | 精简 | 稳态 20 步后就稳定；吞吐和请求率与种子无关 |
| A/B 组的"带通知抢占" | 只跑一种 | 原生 GR00T 不处理 SIGTERM，收到即退出，和硬杀等价 |
| B 组"缓存热" | 删 | 缓存热时等同本地盘，和 A 组下载后一样 |
| X 档 200×（128 GB） | 等 E1 曲线 | 1×/10×/50× 三个点已能看出趋势；本机盘也放不下 |

## 2. 批次

每个批次是一段连续的 GPU 机器时间。纯 CPU 的工作安排在 GPU 空闲时（数据上传、转换期间），**不和计时中的 GPU 运行同时跑**。

### 批次 0：新代码回归 + 抢占修正验证（S 档，约 0.6 GPU 小时，8 次运行）

| # | 运行 | 目的 | 通过标准 |
|---|---|---|---|
| 0a | GCS 直读冷启动 60 步 × 2（默认配置） | 回归：新分支没有变慢，指纹不变 | 首批 ≤ 7 s；启动到第一步 ≤ 46.9 s（native）；60/60 指纹与 `results/v1/cold_steady/lance_v1_gcs` 一致；`startup_summary` 有 7 段；`step.io` 有值 |
| 0b | 同上，`GR00T_LANCE_BG_IMPORT=0` × 1 | 顺带消融：后台导入值多少 | 与 0a 相比 `model_load_s + dataset_build_s` 的差值 |
| 0c | 80 步，save@30，SIGTERM@45，`GR00T_PREEMPT_CKPT_DTYPE=auto` | 自动选档 + 快速退出 | SIGTERM 到退出 < 25 s；`preempt_events.jsonl` 里记下所选档位和实际写盘耗时；恢复后指纹 34/34 |
| 0d | 同上，`=fp32` | 精确档的真实写盘时间 | 指纹 34/34；第 80 步 loss 与 `lance_v1_ref` 相同量级 |
| 0e | 同上，SIGTERM@35（距存档 5 步） | 跳过存档时的退出时间（上次 22.6 s） | SIGTERM 到退出 < 1 s |
| 0f | `--lance-where "is_valid = true"` 冷启动 × 1 | `where` 下仍走 fork | `mp_ctx=fork`；`lance_isolated_s` ≈ 1 s |
| 0g | #5：`bench_lerobot_groot_baseline.py run` 60 步 | LeRobot GR00T 能否直接跑 Lance | 能跑：记首批/步时/内存；跑不通：记阻塞点（这本身就是证据） |

顺带（CPU，GPU 空闲时）：

- E4 纯数据版：`check_exact_resume.py --resume-points random:100:7 --lazy-decode`，同时得到 Lance 精确续训（应 100/100 一致）和原生重设种子的重复率/漏采率。
- 读放大：`bench_loader_io.py`（S 档、GCS、2 轮完整遍历）缓存关 / 开各一次；`--decoder-cache 16` vs `64` 各 400 批看 worker 内存。

### 批次 1：E1 规模冷启动（约 1.4 GPU 小时，27 次短跑）

准备（CPU）：`build_scale_tier_x.py` 生成 1×/10×/50×（0.64 / 6.4 / 32 GB），原始格式和 Lance 都上传到同一个桶（Lance 用 `--lance-uri-template` 直接写桶，不占本地盘）。

| 维度 | 取值 |
|---|---|
| 体积 | 1×、10×、50× |
| 组 | A（s5cmd 下载）、B（rclone 挂载）、C1（Lance 直读） |
| 重复 | 3 次，每次先执行该组复位 |
| 长度 | 到第一步后再跑 20 步 |

产出：图 1（分段堆叠）+ 冷启动 vs 体积曲线。**这 27 次同时就是 E3 里"每次抢占的恢复耗时"**（复位 = 换一台新机器），不用在 E3 里重复测。

决策：B 组也不随体积增长、且和 C1 差距 < 20% → 主卖点从"冷启动快"改为"精确续训 + 省内存 + 改数据便宜"。

### 批次 2：E2 稳态（32 GB，约 0.5 GPU 小时，3 次运行）

| 运行 | 说明 |
|---|---|
| A 下载后 500 步 | 本地盘基线 |
| B 冷缓存 500 步 | FUSE 冷读是 B 组的弱点，热缓存不测 |
| C1 GCS + GOP 缓存 20 GB，500 步 | 每步请求数、每 1k 步请求费、内存（解码器缓存 64） |

数据：M 档（RoboCasa 4 任务）如果已下载完就用 M（更真实），否则用 X 档 50×，报告里写明。

顺带（CPU）：50× 上 `bench_loader_io.py` 前 2,000 批，测每样本请求数（第 2 轮缓存效果用批次 0 的 S 档完整两轮数据；缓存小于数据集时的命中率按"缓存/数据集"估算）。

### 批次 3：E3 抢占（约 2.3 GPU 小时，3 次长跑）

1. **建模（CPU，几分钟）**：用 `preempt_schedule_runner.py --gen-poisson` 生成平均间隔 5 / 10 / 20 分钟 × 2 个种子的时间表，代入批次 0（存档/退出/加载检查点耗时）、批次 1（各组 32 GB 恢复耗时）、批次 2（单步时间），算出三组的"总成本 vs 抢占频率"曲线。
2. **验证（GPU）**：A、B、C1 各跑一次真实 2,000 步，平均 10 分钟一次抢占、种子 1、每 250 步存档、`GR00T_SAMPLE_FINGERPRINTS=1`。A/B 用硬杀，C1 用 SIGTERM + 30 s 后硬杀。
3. **判定**：真实总耗时与模型预测相差 ≤ 10% → 曲线可用；否则补跑 5 分钟间隔的 3 次。

E4：用这 3 次的 `sample_fps` 跑 `analyze_e4_samples.py`；样本量更大的结论来自批次 0 的 100 次纯数据恢复。

## 3. 汇总

| 批次 | GPU 时长 | GPU 运行次数 | 回答的问题 |
|---|---|---|---|
| 0 回归 + 抢占修正 + #5 | 约 0.6 h | 8 | 新代码可用；30 s 内退出；LeRobot 对照 |
| 1 规模冷启动 | 约 1.4 h | 27 | ①大数据冷启动省多少 ②B 组够不够 |
| 2 稳态 32 GB | 约 0.5 h | 3 | 稳态是否持平；请求费 |
| 3 抢占 | 约 2.3 h | 3（+3 备用） | ③抢占下谁更便宜；数据是否重复/漏采 |
| **合计** | **约 4.8 h（最多 7 h）** | **41（最多 44）** | |

## 4. 上机前要准备的

- 把 `feat/v1-next` 部署到 GPU 机器（推送分支或 rsync）。
- 桶里放好 1×/10×/50× 的原始格式和 Lance 两份；GOP 缓存目录放本地盘。
- 先在 GPU 机器上做一次 `--kill-mode term` 短测，确认 SIGTERM 能让 GR00T 主进程走到存档（子任务提醒：信号默认发给整个进程组，worker 可能先退出）。
