# 第二阶段实验设计（v1）

> 承接 [实验方案与 v0 基线结果](experiment-plan.md)。v0 证明了"数据完全正确"和"小数据集稳态持平"，但留下三个没回答的问题：
> **①大数据集上冷启动到底省多少；②挂载方案（B 组）是不是已经够用；③抢占场景下总成本谁低。**
> 本阶段的实验都围绕这三个问题设计，同时把 v0 暴露的短板（首个 batch 慢、续训慢、中断存档贵）作为优化项，逐项做开关对比。

---

## 0. 设计原则

1. **每个结论都配一个可能推翻它的对照组。** 最强对手是 B 组（挂载 + 本地缓存），必须进入所有主实验。
2. **"数据对不对"和"训练效果好不好"分开证明。** 数据用样本级指纹证明，训练效果用多种子区间和仿真成功率。原因见 v0：GPU 非确定性会让同配置两次运行的 loss 在第 100 步差约 0.1。
3. **所有耗时都分段记录原始时间戳**，汇总时再算。不只报总数，评审才能看出时间花在哪。
4. **只改一个变量。** 规模实验固定数据内容只改体积；优化实验固定其他一切，只开关一项优化。
5. **环境限制要补偿，并且写清楚。** 本机是 gVisor 沙箱：不能清页缓存，PSS 不准，不能真正销毁实例，没有 tc。每个实验写明受到哪条限制、怎么补偿。

## 1. 数据集：规模阶梯

| 档 | 数据 | 体积 / 文件数 | 作用 | 状态 |
|---|---|---|---|---|
| **S** | LIBERO-10（AV1 视频，2 路相机 256×256） | 0.64 GB / 1,145 个 | 正确性、稳态基线 | ✅ 已有 |
| **M** | RoboCasa 4 任务（GR00T 官方 `ROBOCASA_PANDA_OMRON`，4 个数据集混合训练） | 约 32 GB / 约 4.8 万个 | 真实的多数据集混合、真实分辨率 | ⏳ 从 HF 下载中（限流） |
| **X** | **受控规模扫描**：把 S 复制 1/10/50/200 份，每份改 episode 编号 | 0.64 / 6.4 / 32 / 128 GB | 只改体积、不改内容，画出"冷启动 vs 体积"、"内存 vs 体积"两条曲线 | ⬜ 新增 |
| **L** | 规模点：RoboCasa 全量 24 任务（353 GB）或 DROID（358 GB） | 约 350 GB | 证明"几百 GB"的真实痛点 | ⬜ 需要决定 |

**为什么加 X 档**：M 和 L 受 HF 限流影响，下载可能要很久；而且真实数据集之间分辨率、编码都不同，体积不是唯一变量。X 档内容完全相同，只有体积在变，是 H1（冷启动）和 H4（内存）最干净的证据。代价是"复制出来的数据"会被质疑不真实，所以它只用来画趋势，结论还要靠 M 和 L 背书。
**存储成本**（GCS 标准存储约 $0.02/GB/月，A 组要原始格式一份，C 组要 Lance 一份）：X 档最大 128 GB × 2 ≈ $5/月；L 档约 $7–14/月。实验结束即删。

**L 档本机的硬约束**：groot 数据盘 196 GB，A 组（先下载）放不下 350 GB。两个办法：
- 甲：A 组在 L 档只测"下载吞吐"（下一半就停），完整时间按吞吐外推，并在报告里写明"本机放不下"本身就是 A 组的一个缺点；
- 乙：L 档换一台 ≥ 500 GB 盘的机器。

推荐甲。

## 2. 对照组（v1）

| 组 | 做法 | "新实例"复位动作（模拟抢占后换了一台机器） |
|---|---|---|
| **A 先下载** | `s5cmd cp` 把原始 LeRobot v2.1 下载到本地盘（并发 256），然后 GR00T 原生训练 | 删除本地数据目录 |
| **B 挂载+缓存** | `rclone mount`（S3 接口，`--vfs-cache-mode full`，缓存放本地盘），GR00T 原生训练直接读挂载目录。等价于 SkyPilot `MOUNT_CACHED` | 卸载挂载，删除 VFS 缓存目录 |
| **C Lance 直读** | v0 实现，`--dataset_path s3://…` | 删除 Lance 元数据本地缓存 |
| **C1 Lance 直读 + v1 优化** | C 加上第 5 节的优化 | 同 C |
| **D Lance 本地** | Lance 表放本地盘 | 不复位（只作为上限参考） |
| **C′ 原生数据+精确续训** | A 的数据路径 + 精确续训，不用 Lance | 同 A |

- A、B、C′ 用的是同一份原始 LeRobot v2.1 文件，C、C1、D 用的是转换后的 Lance 表，两份都放在同一个桶里。
- 所有组都用 GR00T fast loader 的混合/洗牌逻辑，同一种子下样本流逐比特一致（v0 已验证）。
- **B 组可行性已验证**（2026-11-27）：rclone v1.68.2 在 gVisor 里可以挂载桶，但必须用 root 挂载并加 `--allow-other --uid --gid`。普通用户挂载会报"不允许挂在 9p 文件系统上"。粗测结果：单个 MP4（0.7 MB）首次读 0.35 s；**379 个 MP4（376 MB）逐个顺序读，冷读 32.5 s（约 12 MB/s，延迟限制），缓存后 2.2 s**。GR00T 用多个 worker 并行读，实际表现要在 E1/E2 里测。

## 3. 实验清单

### E1 冷启动（H1）

**问题**：从"拉起训练"到"第一个训练步"，各组要多久？时间花在哪一段？随数据体积怎么变化？

| 项 | 设计 |
|---|---|
| 数据 | S、M、X 四档（1/10/50/200 份）；L 档只跑 A 组下载吞吐 + C/C1 |
| 组 | A、B、C、C1 |
| 重复 | 每个格子 5 次，报中位数和最小/最大值 |
| 复位 | 每次开始前执行该组的"新实例"复位动作 |
| 分段（每段一个时间戳） | ①数据准备（下载 / 挂载 / 拉元数据）②进程启动和导入 ③加载模型 ④建数据集（含 GR00T 的统计量计算）⑤创建数据加载器（worker 启动）⑥首个 batch ⑦首个训练步完成 |
| 补偿 | 本机不能清页缓存，所以每次复位都**换一个新的本地目录名**，保证 A/B 组读到的本地文件从未进过缓存 |
| 产出 | **图 1：冷启动分段堆叠条形图**（横轴：组 × 体积）；**附图：冷启动 vs 体积折线**（X 档） |

**判定**：A 组的冷启动应随体积线性增长（斜率约等于 1/下载带宽），C 组应基本不随体积变化。如果 B 组也不随体积变化，H1 的卖点就只剩"对 A 组"。

### E2 稳态训练与资源（H3、H4）

| 项 | 设计 |
|---|---|
| 数据 | S、M |
| 组 | A（下载完以后）、B（缓存热和缓存冷各一次）、C、C1、D |
| 步数 | 2,000 步（单卡约 25 分钟），2 个种子 |
| 指标 | 每步等数据时间和占比；GPU **SM 占用率**（`nvidia-smi dmon -s u`，代替会虚高的 util%）；系统已用内存峰值；每 1k 步对象存储的**请求次数和字节数**（C 组打开 `RUST_LOG=object_store=debug` 数请求，所有组再用网卡收发字节核对）；每样本平均读取字节（读放大） |
| X 档补充 | C 组在 1/10/50/200 份上各跑 300 步，只记内存，画"内存 vs 体积" |
| 产出 | **图 3：稳态等数据占比 + 内存峰值**（按数据集分组）；**表：每 1k 步的请求费用估算**（GCS/S3 读请求单价 × 请求数） |

**判定**：等数据占比 < 5% 算达标；C 组每 1k 步的请求费用要小于 A 组"每次冷启动下载一遍"摊到同样步数上的费用，否则要在报告里讲清楚盈亏平衡点。

### E3 抢占（H2，核心实验）

**问题**：被反复抢占时，各组跑完 N 步要多少时间、多少钱？数据有没有重复或漏掉？

| 项 | 设计 |
|---|---|
| 数据 | M（主），S（快速验证脚本） |
| 组 | A、B、C1，外加 C′（只看数据正确性，不比时间） |
| 训练长度 | 2,000 步 |
| 检查点间隔 | 250 步（主），1,000 步（次，对应 GR00T 默认值） |
| 抢占时间表 | 泊松分布，平均间隔 {5, 10, 20} 分钟训练时间（按本实验长度缩放自方案里的 30/60/120 分钟），每档 2 个固定种子。**所有组用同一份时间表**，预先生成成文件 |
| 抢占方式 | ①硬杀：`SIGKILL`，不给时间；②带通知：`SIGTERM`，30 秒后 `SIGKILL`（对应 GCP spot 的 30 秒通知；AWS 是 120 秒） |
| 恢复流程 | 监督脚本模拟 SkyPilot 托管任务：杀掉 → 执行该组的"新实例"复位 → 等待固定的"开机时间"（不在本机实测，按 0 计，在成本模型里另加 60–180 秒）→ 用 `--resume_from_checkpoint` 重启 |
| 检查点存放 | 主实验存本地盘（本机磁盘不会丢）；另外单独测一次"24 GB 检查点上传/下载到桶"的耗时，加进成本模型 |
| 指标 | 每次恢复耗时（被杀 → 新的第一个训练步，分段）；回滚重做的步数；浪费的 GPU 时间（恢复耗时 + 重做步数 × 单步时间）；跑完 2,000 步的总墙钟和总 GPU 时长；样本重复率、漏采率、与不中断运行的顺序一致率（来自 E4）；最终 loss |
| 规模 | 3 组 × 3 档频率 × 2 种子 × 2 种抢占方式 = 36 次运行，每次约 30–50 分钟。**先跑硬杀（18 次），带通知的视结果再定** |
| 产出 | **图 2：横轴抢占频率，纵轴"完成 2,000 步的总成本"，每组一条线**（核心卖点图）；表：每次恢复的分段耗时 |

**已知要优化的点**：v0 中断时写 24 GB 检查点要 55 秒，比原生重做 50 步还贵。C1 组在这里用"按代价决定存不存"（见第 5 节 #3），否则 C 组在高频抢占下会输。

### E4 样本级数据正确性

| 项 | 设计 |
|---|---|
| 做法 | 每步把 batch 里**每个样本**的 state/action 张量各算一个哈希（v0 只有整批哈希），写进指标文件 |
| 指标 | 以"不中断运行"为准：重复率（同一样本被训练多于应有次数）、漏采率（应训练但没训练）、顺序一致率 |
| 用到哪里 | E3 所有运行；另外补一个纯数据加载的大样本版本（不跑模型，模拟 100 次抢占，几分钟就能跑完） |

### E5 网络扰动（P4b）

| 项 | 设计 |
|---|---|
| 注入方式 | 本机没有 `tc`。用 toxiproxy 做 TCP 层代理：`/etc/hosts` 把 `storage.googleapis.com` 指到本机，toxiproxy 监听 443 原样转发 TLS（证书域名不变，客户端无感）。可注入：延迟 50±20 ms、限速 1 Gbps / 200 Mbps、按比例断连（近似 1% 丢包） |
| 不能注入的 | HTTP 层的 503 SlowDown：TCP 代理看不到 HTTP。替代办法是用对象存储模拟器（如 MinIO）单独测 C 组的重试行为 |
| 组 | B、C1（A 组下载完就不再读网络，只在下载阶段受影响，E1 里顺带测一次） |
| 步数 | 每种扰动 500 步 |
| 指标 | 稳态吞吐、等数据占比、出错/重试次数 |

### E6 清洗与修复（H5）

| 项 | 设计 |
|---|---|
| 转换 | M 档转换耗时、每 GB 耗时；原始 vs Lance 的字节数和对象数 |
| 体检 | 跑 `lerobot-lance-doctor`：耗时，发现的问题数（孤立行、帧数对不上） |
| 修复 | 随机挑 5% 的 episode 当作"坏数据"删除。原始格式：删文件，改 `episodes.jsonl`、`info.json`，重算统计量；Lance：`delete` + `compact` + 更新元数据。比较耗时、改写的字节数、动到的对象数，以及修复后能不能直接接着训练（E1 的流程跑一次） |
| 产出 | 表：转换 / 体检 / 修复的时间和 I/O 成本 |

### E7 训练效果（最终背书，可选）

| 项 | 设计 |
|---|---|
| 做法 | LIBERO-10：A 组和 C1 组各完整训练一次，batch 32、2 万步（单卡约 4 小时/次），然后在 LIBERO 仿真里各评 200 个回合的成功率 |
| 预期 | 两组数据逐比特相同，成功率差别应该在统计误差内（200 回合约 ±3%） |
| 风险 | 仿真环境需要 EGL 渲染，gVisor 下不一定能跑，要先试 |

### E8 v1 优化逐项消融

第 5 节每一项优化单独打开，用 E1（S 和 M 档，各 3 次）和 E3 的短版（S 档、固定 3 次抢占）测效果。每项优化都要报"开 vs 关"的差值，不只报全部打开后的结果。

## 5. v1 优化项（C1 组，E8 逐项验证）

| # | v0 实测问题 | 优化 | 验证指标 |
|---|---|---|---|
| 1 | 首个 batch 19–22 s（原生 7.5 s） | ①加载模型的同时就启动数据加载器并预取首批；②forkserver 预热时顺便打开表；③首次填充洗牌缓冲区时先按小阈值出数（保持顺序确定） | E1 第 ⑤⑥ 段 |
| 2 | 续训冷启动 131 s（原生 71 s） | 先用 #1 的分段埋点定位；怀疑 forkserver 预加载和加载检查点抢 CPU/IO | E3 恢复耗时 |
| 3 | 中断时写 24 GB 检查点 55 s | 按代价决定：只有"距上次存档的步数 × 单步时间 > 预计保存时间"才存；否则直接退出，依赖上一个存档 + 精确续训 | E3 总成本 |
| 4 | 读放大约 45–60 KB/样本（来源和取舍见 [v0 文档](experiment-plan.md) P3 和它的第 5 节 #4） | 只在字节数成为瓶颈时做 | E2 请求数、字节数 |
| 5 | 每个解码线程各带 16 线程解码池 | 每个 worker 共享一个解码池 | E2 CPU 占用 |

## 7. 决策点

| 时间点 | 如果… | 那么… |
|---|---|---|
| E1 跑完 | B 组冷启动也不随体积增长，而且和 C 组差距 < 20% | 价值主张改为"精确续训 + 不爆内存 + 修数据便宜"，不再主打"冷启动快" |
| E8 跑完 | C1 首批仍比原生慢 2 倍以上 | 先解决首批再做 E3，否则高频抢占下 C 组一定输 |
| E3 跑完 | C1 在任何抢占频率下总成本都不低于 A/B | 报告主线改为"正确性"（原生续训会重复和漏采），时间成本如实报持平或略差 |
| 任何时候 | B 组在 gVisor 里性能明显失真（例如 FUSE 开销远高于普通 VM） | B 组搬到普通 VM，或者 E1/E3 在普通 VM 上整体重做一遍 |

**最后的现实验证**（不在本机做）：在 GCP 或 AWS 上用 SkyPilot 跑一次真实 spot 24 小时（A 组和 C1 组各一次），需要 GPU 配额。
